# Чистый переход на многопользовательский сервис

Процедура для отдельного эксплуатационного решения по [#75](https://github.com/an3wers/file-service-demo/issues/75).
Старые пользователь, файлы, каталоги, операции загрузки и объекты бакета не переносятся и не
восстанавливаются. Потеря согласована только для старого состояния этого перехода.
Подготовка процедуры ([#84](https://github.com/an3wers/file-service-demo/issues/84)) сама ничего
не удаляет, не выкладывает и не меняет рабочие секреты.

Команды выполняются из `server/` с `.env` целевого окружения (как `npm run db:migrate`).
Любой непройденный шаг оставляет сервис на обслуживании; откат к старым данным не предусмотрен.

## 1. Перерыв обслуживания

1. Закрыть внешний доступ на внешнем proxy или файрволе: пользователи получают страницу
   обслуживания. Если внешнего proxy нет, остановить и контейнер `client` (это nginx с `/api`).
2. Остановить старое приложение (`docker compose stop server`) и все запуски
   `npm run db:cleanup` и других процессов уборки. Новые операции и выдача ссылок прекращаются.
3. Зафиксировать время остановки `T`.

## 2. Ожидание старых ссылок и обращений к хранилищу

Подписанные ссылки действуют до своего срока независимо от сервиса. До финальной очистки
дождаться `T + max(PRESIGN_UPLOAD_TTL_SECONDS, PRESIGN_DOWNLOAD_TTL_SECONDS,
PRESIGN_PART_TTL_SECONDS) + 5 минут` по значениям **старого** `.env`, до его замены
(с умолчаниями — 1 час 5 минут). Запас покрывает
начатые обращения к хранилищу.

## 3. Новая конфигурация и секреты

В `server/.env` целевого окружения:

- Новые случайные `JWT_ACCESS_SECRET` и `AUTH_CODE_SECRET` (`openssl rand -base64 48`), разные.
  Смена секрета подписи исключает старые токены доступа; старые сессии обновления удаляются очисткой.
- Удалить `LOGIN_USER_APP` и `PASSWORD_USER_APP`: они не используются, пользователь из окружения
  не создаётся.
- `NODE_ENV=production`, `COOKIE_SECURE=true`.
- `AUTH_PUBLIC_URL` — доверенный публичный HTTPS-адрес; `AUTH_ALLOWED_ORIGINS` и `CORS_ORIGIN` —
  тот же origin. Клиент и API обслуживаются с одного origin.
- `NOTIFICATION_ENABLED=true` и `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS_MODE`, `SMTP_USER`,
  `SMTP_PASSWORD`, `SMTP_FROM` (отправитель).
- `TRUSTED_PROXIES` — только фактические адреса или сети reverse proxy.
- `AUTH_RESPONSE_DEADLINE_MS=15000` — общий дедлайн запросов писем. Таймаут ответа proxy —
  не меньше 30 секунд (в `client/nginx.conf` — 300 секунд); клиент не обрывает такие запросы
  раньше proxy. Proxy не журналирует тело и query string запросов `/api/auth`.

## 4. Очистка

1. Пользователь самостоятельно очищает бакет: все объекты и незавершённые составные загрузки
   (abort каждой загрузки удаляет её части).
2. Очистить данные приложения в существующей БД:

   ```bash
   npm run transition -- clean --confirm <DATABASE_NAME>
   ```

   Удаляются строки всех таблиц, кроме `schema_migrations`; схема и история миграций остаются.
   Команда отказывает, если в БД уже есть зарегистрированные пользователи с email. Она не входит
   в старт приложения и не запускается автоматически; после открытия её не выполняют.

## 5. Миграции и проверка чистого состояния

```bash
npm run db:migrate
npm run transition -- verify
```

`verify` завершается кодом 0 только если все таблицы приложения пусты, все миграции применены,
в бакете нет объектов и незавершённых составных загрузок. Применённые миграции не редактируются.

## 6. Проверка перед открытием

Запустить новое приложение при закрытом внешнем доступе (доступ только оператору) и проверить
в рабочем окружении, не подменяя это локальными тестами:

1. HTTPS и cookie: после входа `refresh_token` имеет `HttpOnly`, `Secure`, `SameSite=Strict`,
   `Path=/api/auth`, без `Domain`; запрос с чужим `Origin` к `/api/auth/*` получает отказ.
2. Почта: `npm run notification:test -- --to <ящик оператора>`; письмо активации из регистрации
   содержит ссылку на `AUTH_PUBLIC_URL`.
3. Старый доступ: прежние логин и пароль не дают входа, старый токен доступа получает `401`.
4. Изоляция: зарегистрировать и активировать двух пользователей, загрузить файл первым;
   второй не видит его в списке и получает `404` по его идентификатору.
5. Повторный запуск: перезапустить сервер (`docker compose restart server`); пользователи,
   файлы и сессии сохраняются, `npm run transition -- clean ...` отказывает.

Только после всех пунктов открыть внешний доступ.

## Тестовый прогон порядка перехода

Порядок проверен на отдельной БД без рабочих секретов и данных:
`server/src/db/transition.postgres.test.ts` создаёт старую схему (миграции до
`011_stopped_multipart.sql`) со старым пользователем, каталогом, файлом и операцией загрузки,
выполняет очистку и штатные миграции, проверяет чистое состояние, затем создаёт нового
пользователя с сессией, файлом и операцией загрузки и подтверждает, что повторные миграции их
сохраняют, а очистка отказывает. Второй сценарий очищает БД, где 014 уже применена поверх
файлов без владельца и пользователя из окружения.
Запуск: `npm run test:postgres` (PostgreSQL на `127.0.0.1:55431`, см. `server/README.md`).
