## Вывод

Базовые механизмы защиты реализованы хорошо, но управление сроком и отзывом доступа
слабее рекомендаций OWASP. Основные риски: недостаточная стоимость scrypt,
бессрочное продление постоянного refresh-токена и сохранение выданного доступа
после отзыва сессии.

Это анализ текущей реализации по OWASP Cheat Sheets, а не полная проверка
соответствия OWASP ASVS и не результат тестирования на проникновение.
Приоритеты ниже обозначают порядок работ, а не оценку CVSS.

## Сильные стороны

| Область | Реализованная защита |
| --- | --- |
| Проверка владельца | Владелец берётся из проверенного JWT, а не из тела запроса. Доступ к данным ограничивается через `forOwner(ownerId)`. Идентификаторы операций загрузки привязаны к владельцу. |
| Защита маршрутов | Файлы и каталоги находятся за общим `requireAuth`. Решение о доступе принимает сервер. |
| Создание сессии | Правильного пароля недостаточно: требуется код. Погашение попытки и создание сессии атомарны. |
| Защита от перебора | Лимиты по IP, email и пользователю хранятся в PostgreSQL. Пять неверных кодов завершают попытку; повтор кода не сбрасывает счётчик. |
| Генерация и хранение секретов | Refresh-токены и секреты ссылок генерируются из 32 случайных байтов. В БД хранятся хеши; для короткого кода применяется HMAC с отдельным секретом. |
| Пароли | Случайная соль, scrypt, сравнение через `timingSafeEqual`. Недостаточная стоимость scrypt отдельно описана в замечании 1. |
| Клиентское хранение | Access-токен находится в памяти вкладки. Refresh-cookie имеет `HttpOnly`, `SameSite=Strict` и ограниченный путь. Secure обязателен конфигурацией для разрешённых нелокальных origin. |
| CSRF | Auth-маршруты проверяют точное совпадение `Origin` с разрешённым списком, отклоняют отсутствующий и `null` Origin; дополнительно ограничивают тип тела запроса. |
| Восстановление пароля | Одноразовый секрет, ограниченный срок, нейтральный ответ, выравнивание времени ответа, отзыв прежних сессий и попыток, уведомление об изменении пароля. |
| JWT | Проверяются подпись, срок и назначение токена; разрешён только HS256. |
| Общий вход вкладок | Блокировка запросов авторизации и поколение входа защищают от применения устаревших результатов. |
| Защита секретов в ответах и журналах | Auth-ответы используют `Cache-Control: no-store`; заголовки с cookie и Authorization редактируются при логировании. |

Изоляция по владельцу соответствует направлению рекомендаций
[OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html):
проверять разрешения на каждом запросе и каждом объекте. В прочитанных путях обхода
этой проверки не обнаружено; отсутствие обходов во всём приложении не утверждается.

Проверка Origin вместе с cookie-настройками является содержательной защитой от CSRF.
Отсутствие отдельного CSRF-токена само по себе не означает уязвимость.
См. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## Замечания

### 1. Параметры scrypt ниже рекомендуемых OWASP

**Статус:** подтверждено кодом. **Приоритет:** первая очередь.

Используются параметры `N=16384 (2¹⁴), r=8, p=1`.
Для `N=2¹⁴, r=8` OWASP рекомендует `p=5`; другой рекомендуемый вариант —
`N=2¹⁷, r=8, p=1`. Текущая комбинация не достигает перечисленного минимального уровня.

**Сценарий риска:** при утечке БД атакующий перебирает пароли офлайн.
Лимиты входа этому не мешают. Соль и безопасное сравнение не компенсируют
недостаточную стоимость вычисления хеша.

**Рекомендация:** подобрать рекомендуемые параметры под реальные CPU, память
и параллельность входов. Предусмотреть обновление существующих хешей:
изменение параметров только для новых паролей не усилит старые учётные записи.

**Проверка исправления:** новые хеши используют выбранные параметры; старые пароли
по-прежнему проверяются и переходят на новые параметры по принятому механизму.
Отдельно измерить задержки и расход ресурсов при параллельных запросах.

Код: [scrypt-hasher.ts](../server/src/modules/auth/adapters/crypto/scrypt-hasher.ts).
Источник: [OWASP Password Storage — scrypt](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt).

### 2. Украденный refresh-токен можно поддерживать бессрочно

**Статус:** исправлено по ADR-0013: срок сессии фиксирован, refresh его не сдвигает.
Ниже сохранено описание состояния на момент анализа. Отдельный тайм-аут бездействия и
ротация refresh-токена сознательно не вводились.
**Приоритет на момент анализа:** первая очередь для определения политики сессий.

На момент анализа продление сохраняло секрет refresh-токена и устанавливало
`expires_at = сейчас + 7 дней`. Абсолютного предела от момента входа не было.

**Сценарий риска:** получив refresh-токен, атакующий регулярно вызывает `/refresh`
и сохраняет доступ независимо от активности владельца. Проверка Origin этому
не препятствует: произвольный HTTP-клиент может выставить этот заголовок.
Origin проверяется для защиты от браузерных CSRF-запросов, а не от использования
уже похищенного секрета.

OWASP рекомендует абсолютный срок сессии независимо от активности. Периодическая
замена идентификатора является дополнительной защитой. Семидневное окно без
продления не является абсолютным сроком.

**Рекомендация:** сначала добавить серверный абсолютный срок от момента входа.
Затем отдельно рассмотреть ротацию refresh-токенов с обработкой повторных запросов
и нескольких вкладок. Ротация без абсолютного срока не решает всю проблему.
Изменение требует пересмотра соответствующего решения ADR-0007.

**Проверка исправления:** регулярные продления не позволяют выйти за абсолютную
границу; истёкшая или отозванная сессия не восстанавливается, включая гонки запросов.

**Результат исправления:** сессия получает `expires_at = момент проверки кода + 14 × 24 часа`.
Refresh проверяет границу (на равенстве отклоняет с 401 SESSION_EXPIRED), отзыв и активность
пользователя, но не меняет ни срок, ни секрет, ни cookie. Проверено PostgreSQL-интеграционными
тестами с управляемыми часами: граница, параллельные refresh через два экземпляра и перезапуск,
перепроверка срока после ожидания блокировки, сессия со старым назначенным сроком. Остаточный
доступ выданного JWT (до 15 минут после границы) и сроки подписанных ссылок остаются принятым
риском замечания 3.

Код: [sql-session-store.ts](../server/src/modules/auth/adapters/persistence/sql-session-store.ts).
Источник: [OWASP Session Management — Automatic Session Expiration](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#automatic-session-expiration).

### 3. Отзыв сессии не прекращает весь выданный доступ

**Статус:** подтверждено кодом. **Приоритет:** первая очередь для ссылок;
для немедленного отзыва JWT — решение по требованиям к данным.

#### Access JWT продолжает действовать до 15 минут

После выхода или восстановления пароля ранее выданный JWT продолжает работать.
Сервер проверяет подпись и срок без проверки состояния сессии. Удаление токена
клиентом не мешает использовать ранее скопированную версию.

**Сценарий риска:** атакующий после отзыва сессии продолжает выполнять операции
с файлами до истечения access-токена.

OWASP описывает расхождение JWT и состояния сессии и рекомендует механизм отзыва,
например denylist. Текущий остаточный доступ принят в ADR-0007, но остаётся риском.

**Рекомендация:** определить требуемую скорость прекращения доступа. Если отзыв
должен действовать немедленно, нужна проверяемая сервером связь JWT с сессией
либо другой механизм отзыва. Сокращение TTL только уменьшает окно.

Код: [jose-tokens.ts](../server/src/modules/auth/adapters/tokens/jose-tokens.ts).
Источник: [OWASP REST Security — JWT](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#jwt).

#### Ссылку скачивания можно запросить на семь дней

API допускает запрос:

```http
GET /api/files/:id/download-url?expiresIn=604800
```

Переданное значение используется вместо `policy.presignDownloadTtlSeconds`.
Поэтому срок по умолчанию в пять минут не ограничивает максимальный срок ссылки.

**Сценарий риска:** атакующий с действительным JWT получает длительную ссылку
и затем скачивает файл напрямую из хранилища после истечения JWT и отзыва сессии.
Это не обход проверки владельца: доступ был делегирован ссылкой, но срок
делегирования затрудняет быстрое прекращение доступа.

**Рекомендация:** ограничить срок ссылок серверной политикой. Если нужен немедленный
отзыв уже выданных ссылок, одного сокращения TTL недостаточно — потребуется отдельно
выбрать механизм контролируемого скачивания или отзыва доступа к объекту.

**Проверка исправления:** клиентский `expiresIn` не может превысить серверный предел.
Отдельно проверить поведение JWT после выхода и сброса пароля согласно выбранной
политике. Существующий тест выдачи ссылки проверяет срок по умолчанию, но не
подмену срока через `expiresIn`.

Код: [downloadUrlQuerySchema](../server/src/modules/files/adapters/http/schemas.ts),
[getDownloadUrl](../server/src/modules/files/application/catalog.ts),
[тесты владения](../server/src/modules/files/adapters/http/ownership.postgres.test.ts).

### 4. Политика паролей допускает очевидные и скомпрометированные пароли

**Статус:** подтверждено в исследованном пути регистрации и сброса.
**Приоритет:** следующая очередь.

Принимаются пароли от 12 до 128 символов. Например, `aaaaaaaaaaaa` проходит
проверку длины. Проверки распространённых и скомпрометированных паролей нет.

Положительные свойства текущей политики: поддерживаются длинные пароли и Unicode,
нет обязательных искусственных комбинаций символов.

**Сценарий риска:** пользователь выбирает предсказуемый пароль, который легко
попадает в словари перебора. Email-код уменьшает риск входа с одним паролем,
но не делает такой пароль надёжным.

OWASP рекомендует блокировать распространённые и утёкшие пароли. Ориентиры длины:
не менее 8 символов с MFA и 15 без него. Минимум 12 нельзя оценивать отдельно
от надёжности второго фактора, описанной в замечании 5.

**Рекомендация:** добавить серверную проверку запрещённых паролей и одинаково
применять её при регистрации и сбросе. Минимум длины выбрать вместе с решением
о втором факторе.

**Проверка исправления:** известные слабые пароли отклоняются обоими маршрутами;
длинные допустимые парольные фразы и Unicode продолжают работать.

Код: [schemas.ts](../server/src/modules/auth/adapters/http/schemas.ts),
[registration.ts](../server/src/modules/auth/application/registration.ts).
Источник: [OWASP Authentication — Password Strength Controls](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#implement-proper-password-strength-controls).

### 5. Почта остаётся единой точкой компрометации аккаунта

**Статус:** ограничение модели доверия. **Приоритет:** зависит от чувствительности файлов.

Email-код полезнее одного пароля, но его нельзя безоговорочно считать независимым,
устойчивым к фишингу вторым фактором.

**Сценарий риска:** захватив почту, атакующий сбрасывает пароль сервиса, затем
получает на ту же почту код входа. Оба этапа контролируются через один канал.
OWASP отмечает зависимость email-подтверждения от безопасности почтового аккаунта
и его уязвимость к фишингу.

**Рекомендация:** для чувствительных файлов рассмотреть passkeys/WebAuthn либо
независимый дополнительный фактор. Восстановление доступа должно сохранять его
защиту: добавление TOTP не поможет против захвата почты, если фактор можно снять
только через тот же почтовый аккаунт.

Это не ошибка генерации или проверки шестизначного кода.

Код: [sessions.ts](../server/src/modules/auth/application/sessions.ts),
[registration.ts](../server/src/modules/auth/application/registration.ts).
Источник: [OWASP Multifactor Authentication — Email](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#email).

### 6. Защитные заголовки страницы не закреплены в конфигурации репозитория

**Статус:** подтверждено для просмотренной конфигурации; production требует проверки.
**Приоритет:** проверить при развёртывании, затем устранить подтверждённые пробелы.

В проверенных Express/nginx-конфигурациях не найдены CSP, защита от встраивания
страницы через `frame-ancestors`/`X-Frame-Options`, `X-Content-Type-Options` и HSTS.
Внешний reverse proxy может добавлять их; его конфигурация не проверялась.

**Сценарий риска:** при наличии XSS скрипт на доверенном origin может вызвать
`/refresh`, прочитать выданный JWT и выполнять действия пользователя. `HttpOnly`
запрещает чтение refresh-cookie, но не такие действия скрипта.
Отсутствие CSP само по себе не доказывает наличие XSS.

**Рекомендация:** проверить реальные ответы сайта. Настроить CSP для SPA,
запретить ненужное встраивание страницы, добавить `nosniff`; HSTS настраивать
на внешней HTTPS-границе. Политика должна учитывать реальные подключения
приложения, включая прямые обращения к объектному хранилищу.

**Проверка исправления:** заголовки присутствуют в ответах рабочего сайта;
вход, обновление сессии, загрузка и скачивание работают с выбранной политикой.

Код: [nginx.conf](../client/nginx.conf), [app.ts](../server/src/app.ts).
Источник: [OWASP HTTP Headers](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html).

### 7. Журналы недостаточны для расследования захвата аккаунта

**Статус:** подтверждено для логирования приложения; внешняя система наблюдения не проверялась.
**Приоритет:** следующая очередь.

Есть HTTP-логи, ошибки и события отправки писем. Не найдены отдельные события
создания, продления и отзыва сессии с безопасным идентификатором пользователя
или сессии. Сериализатор запроса сохраняет только ID запроса, метод и путь.

**Сценарий риска:** после сообщения о захвате аккаунта сложно восстановить,
какие входы и продления относились к нему и откуда выполнялись.
Это недостаток расследования и обнаружения, а не отсутствие всех журналов.

**Рекомендация:** добавить структурированные события успешного и неуспешного
входа, создания и отзыва сессии, сброса пароля. Определить безопасные поля
корреляции и политику хранения. Не записывать токены, коды и пароли.

**Проверка исправления:** по событиям можно восстановить жизненный цикл сессии
и связать ошибки входа; секреты отсутствуют в успешных и ошибочных сценариях.

Код: [app.ts](../server/src/app.ts), [logger.ts](../server/src/logger.ts),
[mail-log.ts](../server/src/modules/auth/application/mail-log.ts).
Источник: [OWASP Logging — Which Events to Log](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#which-events-to-log).
