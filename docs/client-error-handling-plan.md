# Клиент: поддержка нового слоя ошибок сервера

## Context

Сервер переработал обработку ошибок (`server/src/errors.ts`, `s3/errors.ts`, `db/errors.ts`,
`middleware/error-handler.ts`; контракт описан в [`server/README.md`](../server/README.md), раздел
«Ошибки»). Что изменилось для клиента:

1. **Появилось 8 новых кодов.** Раньше любой сбой S3 или PostgreSQL приходил как
   `500 INTERNAL_SERVER_ERROR`; теперь это `STORAGE_*` (502/503), `DATABASE_*` (503),
   `DUPLICATE_RESOURCE` (409), `UPLOAD_REJECTED` (400), `ROUTE_NOT_FOUND` (404).
2. **502 и 503 разведены намеренно.** 503 — зависимость не ответила, повтор имеет смысл; 502 —
   сломана конфигурация сервера, повтор бесполезен. Это единственное, ради чего сервер вообще
   перестал схлопывать всё в 500, и сейчас клиент этим сигналом не пользуется.
3. **В теле ошибки появился `requestId`** — тот же id, что и в строке лога `pino-http`. Клиент его
   не читает, поэтому по жалобе пользователя найти причину в логе невозможно.
4. **Ошибки multer нормализованы**: вместо `LIMIT_FILE_SIZE` приходит `PAYLOAD_TOO_LARGE`, а исходный
   код лежит в `details.multerCode`.

Пока клиент не обновлён, ничего не ломается: `errorMessage` в `src/lib/errors.ts` для неизвестного
кода откатывается на `error.message` с сервера. Но пользователь видит английский текст вместо
русского и не получает ни повтора, ни номера обращения.

## A. Контракт — обязательный минимум

Без этих трёх задач изменения сервера пользователю не видны.

### A1. Восемь новых кодов в `MESSAGES`

**Файл:** `src/lib/errors.ts`

```ts
  STORAGE_UNAVAILABLE: "Хранилище временно недоступно — попробуйте ещё раз",
  STORAGE_MISCONFIGURED: "Хранилище отклонило запрос: на сервере не тот бакет или ключи",
  STORAGE_ERROR: "Ошибка хранилища — операция не выполнена",
  DATABASE_UNAVAILABLE: "База данных недоступна — попробуйте ещё раз",
  DATABASE_TIMEOUT: "База данных не ответила вовремя — попробуйте ещё раз",
  DUPLICATE_RESOURCE: "Такая запись уже существует",
  UPLOAD_REJECTED: "Форма загрузки отклонена: отправьте ровно один файл",
  ROUTE_NOT_FOUND: "Метод API не найден — клиент и сервер разошлись по версиям",
```

Там же:

- добавить `UNKNOWN` — его выдаёт `parseErrorBody`, когда тело ответа не разобралось (прокси отдал
  HTML, оборвалось соединение); сейчас пользователь видит голое `HTTP 500`;
- удалить `LIMIT_FILE_SIZE` — сервер его больше не отдаёт, всегда `PAYLOAD_TOO_LARGE`.

**Готово, когда:** список ключей `MESSAGES` покрывает все 18 кодов из `ERROR_CODES`
(`server/src/errors.ts`) плюс клиентские `NETWORK_ERROR`, `S3_UPLOAD_FAILED`, `UNKNOWN`.

### A2. `requestId` в типе ответа

**Файл:** `src/types/api.ts:70`

```ts
export interface ApiErrorBody {
  error: { code: string; message: string; details?: unknown; requestId?: string | number }
}
```

Заодно комментарий на строке 74: `details` у 422 — теперь результат `z.flattenError()`, а не
`z.flatten()`. Форма `{ formErrors, fieldErrors }` та же, менять `ValidationDetails` не нужно.

### A3. `requestId` доезжает до `ApiError`

**Файл:** `src/api/client.ts`

- поле `requestId?: string | number` в классе `ApiError` (помнить про `erasableSyntaxOnly`:
  параметры-свойства запрещены, присваивать в теле конструктора);
- `parseErrorBody` возвращает его четвёртым полем — только из ветки JSON-ответа сервера; у XML от S3
  и у фолбэка `UNKNOWN` его нет;
- проброс в обе точки создания ошибки: `apiRequest` и `apiUpload`.

**Готово, когда:** в devtools у пойманной `ApiError` от любого 5xx видно `requestId`, совпадающий с
`req.id` в выводе сервера.

## B. Поведение — ради чего сервер разделил 502 и 503

### B1. `isRetryable(error)`

**Файл:** `src/lib/errors.ts`

`true` для `status === 503` и для `status === 0` (`NETWORK_ERROR`, `S3_UPLOAD_FAILED` — браузер не
дал деталей). `false` для 502: там сломана конфигурация сервера, и повтор её не починит. Для
остального — `false`.

Это тот самый сигнал, которого раньше не существовало: до изменений и «S3 моргнул», и «протухли
ключи» приходили одним и тем же 500.

### B2. Повтор там, где ошибка терминальная

**Файлы:** `src/composables/useFileBrowser.ts:94`, `src/composables/useFileActions.ts:27,51`

- В `useFileBrowser` в состояние ошибки сейчас кладётся только строка. Нужен ещё флаг
  повторяемости, чтобы в UI списка рядом с текстом появилась кнопка, вызывающая `refresh()`.
- В `useFileActions` тосты `download` и `remove` для повторяемой ошибки получают `action` с
  повтором самого действия (`vue-sonner` это поддерживает).

**Готово, когда:** при остановленном сервере хранилища список файлов показывает «Повторить», а при
испорченных ключах S3 (502) — не показывает.

### B3. Ретрай `completeUpload` не только на `UPLOAD_NOT_COMPLETED`

**Файл:** `src/composables/useUpload.ts:105-116`

Логика «подождать 800 мс и повторить один раз» уже есть — она про то, что объект в S3 виден не
мгновенно. Теперь `completeUpload` может упасть и с `STORAGE_UNAVAILABLE` (сервер не достучался до
S3 при `HeadObject`) — по смыслу это тот же временный сбой, а обрабатывается как терминальный.
Условие расширить до `code === "UPLOAD_NOT_COMPLETED" || status === 503`.

Важно не трогать соседний комментарий про то, что при падении `putToPresignedUrl` вызывать
`complete` не нужно: запись остаётся `pending` и её разбирает серверный `npm run db:cleanup`.

## C. Чистка

### C1. Сравнение по коду вместо статуса

**Файл:** `src/components/UploadPanel.vue:191`

`error.status === 413` → `error.code === "PAYLOAD_TOO_LARGE"`. Код теперь гарантирован сервером, а
статус 413 в будущем может прийти и от чего-то другого. Подсказку про режим «Напрямую в S3»
оставить как есть.

### C2. Номер обращения в интерфейсе

**Файлы:** `src/components/UploadPanel.vue`, `src/composables/useFileActions.ts`,
`src/composables/useFileBrowser.ts`

Для `status >= 500` дописывать в `description` тоста (или в блок ошибки списка) «Код обращения: N».
Без этого A3 не имеет смысла: пользователь не может сообщить ничего, по чему в логе находится
причина.

---

## Порядок

`A1`, `A2`, `A3` независимы друг от друга и делаются за один заход; `A3` разблокирует `C2`, а `B1` —
`B2` и `B3`. `C1` можно делать в любой момент.

`A` и `C1` — чистая поддержка контракта, поведение приложения не меняют. `B` и `C2` меняют.

## Проверка

Сценарии воспроизводятся подменой окружения сервера (см. раздел «Проверка» в
[`server/README.md`](../server/README.md) — там же ожидаемые коды):

| Что делаем | Что должен показать клиент |
|---|---|
| `S3_ENDPOINT` на закрытый порт, загрузка через сервер | русский текст `STORAGE_UNAVAILABLE` + «Повторить» |
| испорченный `KEY_SECRET`, загрузка через сервер | русский текст `STORAGE_MISCONFIGURED`, **без** «Повторить» |
| остановить PostgreSQL, открыть список | `DATABASE_UNAVAILABLE` + «Повторить» |
| файл больше `MAX_UPLOAD_SIZE_MB` | прежняя подсказка про presigned-режим (ветка по коду, не по статусу) |
| `?limit=0` через devtools | 422 с разбором `fieldErrors` — не сломалось после `z.flattenError` |
| любой 5xx | в тосте виден «Код обращения», совпадающий с `req.id` в логе сервера |
