# Контракт API выводится из Zod-схем и лежит в репозитории файлом

OpenAPI-описание HTTP API не пишется руками: его собирает сервер из тех же Zod-схем, которыми
валидирует запросы, плюс Zod-схем ответов. Результат — `server/openapi.json` — коммитится, а
клиент генерирует из него свои типы (тоже коммитит их) вместо ручного зеркала. Тест сервера
падает, если файл разошёлся с кодом.

## Почему не иначе

- **Спецификация руками (design-first).** Валидация запросов на Zod уже есть; отдельный YAML
  стал бы вторым источником истины, который расходится с первым молча. Выкинуть Zod ради
  валидации по спецификации — шаг назад по выразительности правил.
- **JSDoc-аннотации над роутами.** Тот же второй источник, только ещё и без связи с
  реальной валидацией.
- **Клиент тянет схему с запущенного сервера.** Сборка клиента начала бы зависеть от живого
  бэкенда, а изменение контракта не было бы видно в диффе. `server/` и `client/` — независимые
  пакеты без workspace, и Docker-сборка клиента видит только `client/`; файл в репозитории —
  единственная честная связь между ними.

## Следствия

- Сгенерированный файл в git — сознательно. Правка контракта видна в ревью как дифф
  `openapi.json` и типов клиента; тест свежести не даёт закоммитить код без обновлённого файла.
- У ответов появляются Zod-схемы в HTTP-адаптере. Ответы по ним в рантайме не проверяются:
  соответствие типов сценариев схеме ответа проверяет компилятор. Сценарии, как и прежде,
  про HTTP не знают ([ADR-0005](./0005-sloi-i-granitsa-modulya-files.md)).
- Пути описаны дважды — в роутере Express и в описании документа; расхождение ловит тест,
  сверяющий зарегистрированные маршруты с документом.
- Коды ошибок в контракте остаются строкой: список `ERROR_CODES` на клиент пока не
  выводится.
