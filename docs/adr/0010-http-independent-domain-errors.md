# Ошибки домена не знают про HTTP

В модуле `files` ошибки бросаются одной идиомой: домен и сценарии создают только классы из
`domain/errors.ts`, а HTTP-статус и код ответа выбирает HTTP-адаптер модуля
(`adapters/http/error-map.ts`). Отображение сохраняет `details` и исходную ошибку как `cause`.
Глобальный обработчик ошибок модулей не перечисляет: он получает список отображений от
сборки приложения (`composition.ts`), и новый модуль добавляет туда своё.

## Почему

Раньше рядом жили три идиомы: доменные классы, `AppError` со статусом прямо из правил Плана,
составной загрузки и маппера строк, и голый `Error` в memory-двойнике. Из-за этого одно и то же
состояние давало разные ответы на двойнике и на PostgreSQL (повторное резервирование готового
файла: 500 в тестах, 404 в работе), а отображения, написанные вручную, теряли `details`.

## Что решено отдельно

- **Невозможная строка метаданных — доменная ошибка.** Маппер строк бросает
  `ImpossibleFileRowError`; адаптер превращает её в 500 и отправляет её подробности только в лог.
- **Ошибки общей инфраструктуры не переводятся.** `AppError` из `db/pool.ts` и `storage/`
  создаётся вне модуля и проходит сценарии насквозь; сценарии такие ошибки не создают.
- **Двойники повторяют типы ошибок SQL-адаптеров.** Это проверяет общий контракт,
  запускаемый и на двойнике, и на PostgreSQL.
- **Линтер запрещает `domain/` и `application/` импортировать `src/errors.ts` и
  `src/db/errors.ts`.** Для этого правила `no-restricted-imports` собраны в один блок на
  группу файлов: в flat config последний подходящий блок заменяет опции правила целиком, и
  прежние отдельные блоки границ модулей отменяли правила слоёв.

## Следствия

- Коды ошибок HTTP-контракта не изменились; `openapi.json` прежний.
- У модуля уведомлений нет HTTP-маршрутов, поэтому отображения для него нет. Когда маршрут
  появится, модуль добавит отображение в сборку, не меняя обработчик.
