# У живой составной загрузки план обязателен

Строка метаданных с живой составной загрузкой обязана нести размер, размер части и их количество.
Это проверяет ограничение в базе, а код, встретив такую строку без плана, поднимает внутреннюю
ошибку вместо того, чтобы досчитать недостающее.

## Почему это не очевидно

Досчитать выглядит дешевле и добрее: размер восстанавливается из размера части и их количества, и
клиент получает ответ вместо пятисотки. Так и было написано.

## Цена альтернативы

План строится один раз при старте загрузки, и части уже лежат в хранилище нарезанными по его
границам. Досчитанный план — это другой план: он совпадёт с исходным только если ровно те поля,
которых не хватает, были выведены из тех, что остались. Выдав по нему подписанные ссылки, сервис
предлагает клиенту залить часть по диапазону, не совпадающему с уже загруженными, и собранный
объект молча окажется битым. Ошибка при сборке была бы лучше, но обнаружится она у пользователя, а
не в логе.

Вторая цена — ветка, для которой невозможно написать тест: чтобы в неё попасть, нужна строка,
которую не создаёт ни один путь кода. Такая ветка живёт вечно и объясняет читателю несуществующее
состояние.

## Следствия

- Состояние запрещено в базе (`files_multipart_plan_check`), а не только в коде: запись без плана
  теперь невозможна, а не маловероятна.
- Строки, оставшиеся без плана до этого правила, миграция переводит в неудавшиеся: закончить их всё
  равно нечем, а уборка сделала бы то же самое по истечении TTL.
- Отсутствие плана у живой загрузки — 500 с подробностями в логе и без них в ответе: это дефект
  сервиса, а не ошибка клиента.
