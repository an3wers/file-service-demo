# Файловый сервис

Демо-сервис хранения файлов: REST API на Express поверх Cloud.ru Object Storage (S3-совместимое) с
метаданными в PostgreSQL и одностраничный клиент на Vue 3. Файлы лежат в объектном хранилище, а всё,
что о них известно — исходное имя, папка, размер, статус, — живёт в базе.

| Часть     | Что это                               | Документация                         |
| --------- | ------------------------------------- | ------------------------------------ |
| `server/` | REST API, S3 и PostgreSQL             | [server/README.md](server/README.md) |
| `client/` | SPA: загрузка, список, карточка файла | [client/README.md](client/README.md) |
| `docs/`   | планы, по которым сервис собирался    | —                                    |

Каждый README самодостаточен: переменные окружения, маршруты, устройство модулей и тесты описаны
там, а не здесь.

## Возможности

**Три сценария загрузки, одна и та же запись на выходе.** Через сервер — обычная
`multipart/form-data`-форма, байты идут через API, потолок задаёт `MAX_UPLOAD_SIZE_MB`. Напрямую в
хранилище — клиент получает presigned-ссылку и льёт файл сам, минуя процесс API. Частями — для
файлов от `MULTIPART_THRESHOLD_MB`: сервер присылает готовый план (`offset`/`size`/`url` каждой
части), клиент исполняет его параллельно. Для остального интерфейса все три неразличимы.

**Multipart переживает сбои.** Части льются с ограниченной параллельностью, протухшую подпись
заменяет `part-urls`, а `GET /:id/multipart` отвечает тем, что реально лежит в S3, — поэтому
прерванная загрузка продолжается с уже залитого, в том числе после перезагрузки страницы. Брошенную
загрузку клиент отменяет сам. Сервер каждые 15 секунд выполняет уборку и повторяет сохранённые
отмены и удаления; разовый проход можно запустить через `npm run db:cleanup`.

**Папки поверх плоского хранилища.** В S3 папок нет: структуру даёт директория, которая становится
префиксом ключа объекта. Она же — единственный недоверенный ввод, попадающий в ключ, поэтому
нормализация отвергает `..` и управляющие символы, а не переписывает их. Дерево папок строится из
сохранённых путей, `fileCount` считает всё поддерево.

**Список с поиском, сортировкой и пагинацией.** Поиск идёт по текущей папке и подпапкам, сортировка
— по дате, имени или размеру, лимит страницы ограничен сверху сервером.

**Скачивание по временной ссылке.** Клиент не проксирует байты: он переходит по presigned-GET.
`Content-Disposition` восстанавливает исходное имя файла, включая не-ASCII, через RFC 5987
`filename*` — при том, что в хранилище объект называется `<uuid>.<ext>`.

**Ошибки со стабильными кодами.** Каждый провал API — это `{ error: { code, message, details?,
requestId } }`; клиент переводит `code` в текст и показывает «Код обращения», по которому причина
ищется в логе сервера. Внутренности зависимостей (SQLSTATE, имена ошибок AWS, ключи объектов) в
ответ не попадают. 502 и 503 разделены намеренно: повторять стоит только второе, и кнопка «Повторить»
появляется ровно там, где повтор осмыслен.

Оба режима загрузки сохраняют идентичность операции при ручном повторе в той же строке.
Если ответ потерян, кнопка «Выяснить результат» проверяет исходную операцию: готовый файл
становится успехом, а после подтверждённой неудачи можно повторить загрузку или изменить
режим этой строки. Ошибка подтверждения позволяет повторить подтверждение уже переданных
байтов. Отменённую строку можно запустить снова; удалённый успешный результат старая
операция не воссоздаёт. При общем лимите составных загрузок повтор запускается вручную.
Состояние выбранных файлов сохраняется только до закрытия вкладки.

## Быстрый старт

Нужны Docker (для PostgreSQL), бакет в Cloud.ru Object Storage и Node 20.19+ / 22.12+
(в репозитории — 24).

Все команды ниже выполняются из корня репозитория.

```bash
npm ci
cp client/.env.example client/.env
cp .env.example .env
docker compose up -d postgres
```

В корневом `.env` задайте пароль PostgreSQL; БД слушает только `127.0.0.1`.

Создайте `server/.env` по [server/README.md](server/README.md), затем подготовьте окружение:

```bash
npm run db:migrate
npm run s3:cors
npm run dev
```

Миграции применяются идемпотентно; `s3:cors` нужен один раз на бакет. Сервер доступен на
`http://localhost:3000`, клиент — на `http://localhost:5173`. `npm run dev` запускает их
параллельно с префиксами логов `server` и `client`. Ctrl+C останавливает оба дерева процессов;
если один процесс завершается, второй также останавливается.

Порт клиента закреплён: CORS бакета настроен ровно на `http://localhost:5173`, и молчаливый сдвиг на
5174 сломал бы presigned-загрузку. Запросы к API идут через vite-прокси, так что CORS сервера в
разработке не участвует.

## Управление из корня

`server/` и `client/` — npm workspaces с единым корневым `package-lock.json`.
Зависимости объявляются в `package.json` соответствующего сервиса. Корневой `.npmrc` задаёт
`install-strategy=nested`: зависимости сервисов устанавливаются в их `node_modules`,
без hoisting в корень. Это допускает дублирование пакетов и увеличивает объём установки.
В корне объявлен только служебный `concurrently`; корневой `node_modules` также содержит
ссылки на workspace-пакеты.

| Команда                                     | Действие                                                             |
| ------------------------------------------- | -------------------------------------------------------------------- |
| `npm run dev`                               | Параллельный запуск сервера и клиента                                |
| `npm run dev:server` / `npm run dev:client` | Запуск одного сервиса                                                |
| `npm run build`                             | Сборка обоих пакетов в их `dist/`                                    |
| `npm start` / `npm run preview`             | Запуск собранного сервера / предпросмотр клиента                     |
| `npm run typecheck`                         | Проверка типов обоих пакетов                                         |
| `npm run lint` / `npm run lint:fix`         | Проверка / исправление ESLint в обоих пакетах                        |
| `npm test` / `npm run test:watch`           | Обычный прогон / параллельный watch-режим тестов                     |
| `npm run format` / `npm run format:check`   | Форматирование / проверка файлов обоих пакетов                       |
| `npm run check`                             | Последовательно проверка типов, линтер и тесты; остановка при ошибке |
| `npm run test:postgres`                     | Отдельные серверные тесты с PostgreSQL                               |
| `npm run db:migrate` / `npm run db:cleanup` | Миграции / уборка незавершённых загрузок                             |
| `npm run s3:cors`                           | Настройка CORS бакета                                                |
| `npm run openapi`                           | Генерация серверного OpenAPI-контракта                               |
| `npm run api:generate`                      | Генерация OpenAPI, затем клиентских типов                            |

Конечные общие команды выполняются последовательно: сначала `server`, затем `client`.
Команды пакетов работают в своих каталогах и используют локальные `.env` и конфигурации.
Чтобы выполнить проверку для одного пакета или передать ему параметры, используйте
`npm run <script> -w server` или `-w client`, например `npm run test -w client -- src/lib/parts.test.ts`.

Установка и управление зависимостями выполняются из корня:

```bash
npm ci
npm install <package> -w server
npm install -D <package> -w client
npm uninstall <package> -w server
npm update -w client
npm outdated --workspaces
```

Изменённые `package.json` пакета и корневой `package-lock.json` коммитятся вместе.
После перехода с отдельных пакетов выполните `npm ci`, чтобы заменить старое дерево зависимостей.

## Docker

Сборки используют корень репозитория как контекст и единый lock-файл. Каждая устанавливает
зависимости только своего workspace; серверный runtime устанавливает только production-зависимости.
Сервер получает переменные окружения через Compose из `server/.env`. Клиентский `client/.env`
читается при сборке, поэтому изменение его значений требует пересборки клиента.
`server/.env` исключён из обоих Docker-контекстов; для клиентской сборки разрешён `client/.env`.

```bash
docker compose build
docker compose up -d
```

Для сборки отдельных образов команды также запускаются из корня:

```bash
docker build -f server/Dockerfile -t file-storage-server .
docker build -f client/Dockerfile -t file-storage-client .
```

PostgreSQL поднимается в том же Compose с настройками из корневого `.env`; данные хранятся
в томе `postgres_data`. Подключение сервера к БД Compose задаёт сам, перекрывая `DATABASE_*`
из `server/.env`. Миграции перед первым запуском: `npm run db:migrate` с хоста.
Клиент доступен на порту `5173` и проксирует API на сервер во внутренней сети Compose.

### Полезные команды

Все команды выполняются из корня репозитория.

```bash
# Только PostgreSQL — для локальной разработки через npm run dev.
# --wait возвращает управление, когда healthcheck БД пройден.
docker compose up -d --wait postgres
npm run db:migrate

# Весь стек; --build пересобирает образы после изменений в коде.
docker compose up -d --build

# Пересобрать и перезапустить один сервис.
docker compose up -d --build server

# Применить правку server/.env без пересборки образа.
docker compose up -d server

# Состояние сервисов и логи.
docker compose ps
docker compose logs -f server
docker compose logs -f --tail=100 postgres

# Консоль psql внутри контейнера БД.
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

# Остановить, не удаляя контейнеры.
docker compose stop

# Удалить контейнеры и сеть; том postgres_data с данными сохраняется.
docker compose down

# Удалить вместе с томом — база будет создана заново и потребует db:migrate.
docker compose down -v
```

## Стек

Сервер — Express 5, TypeScript, `pg`, AWS SDK v3, zod, pino, multer. Клиент — Vue 3
(`<script setup>`), TypeScript, Vite, Tailwind CSS v4, shadcn-vue, `vue-router`, `vue-sonner`, `@vueuse/core`.
Тесты с обеих сторон — Vitest (`npm test` из корня запускает оба пакета).

## Границы демо

- **Доступ** — регистрация, активация email и вход по паролю и коду; серверные сессии с постоянным токеном обновления, фиксированным сроком 14 суток от входа и отзывом при выходе. Пользователь из окружения больше не создаётся. Повтор кода доступен без пароля в пределах попытки. Файлы и каталоги личные, вкладки одного браузера используют общий вход. Сервис открывается только после [чистого перехода](docs/transition.md) в рабочем окружении.
- **Удаление мягкое в базе и best-effort в хранилище**: источник истины — запись, поэтому её выводят
  из обращения первой.
- **Проверки**: HTTP и клиентские тесты используют подмены; атомарность и конкуренция дополнительно проверяются через `npm run test:postgres`.

Страница `/password-reset` запрашивает письмо восстановления и по ссылке сохраняет новый пароль
с подтверждением, без автоматического входа. Секрет из fragment хранится только в sessionStorage
вкладки; если ссылка принадлежала текущему пользователю, его сессии в браузере завершаются.

Страница `/activation` подтверждает email только кнопкой, без создания или переключения сессии.
Ссылка действует 24 часа; повтор письма отменяет прежнюю ссылку до отправки. При задержке или
сбое SMTP автоматической досылки нет: новое письмо запрашивается вручную на той же странице.
Обновление страницы сохраняет форму в текущей вкладке; после закрытия вкладки или ухода нужно
снова открыть письмо. Регистрация и повтор используют общие email- и IP-квоты.

### Восстановление загрузок

Результат после сбоя связи проверяется автоматически. Через 60 секунд без подтверждения
интерфейс показывает ошибку и продолжает проверку в фоне. Временная подтверждённая неудача
допускает две автоматические повторные попытки; после их исчерпания остатки удаляются.
Отмена удаляет и уже сохранённый файл. Сервер сохраняет задачи очистки в PostgreSQL и
повторяет их после перезапуска, включая удаление поздних объектов по старым ссылкам.

В том же браузере список и намерения отмены сохраняются между входами и перезагрузками.
Содержимое файлов не сохраняется: если для ручного повтора после перезагрузки нужны байты,
кнопка «Повторить» предложит выбрать исходный файл. Перед запуском обновлённого сервера
выполните `npm run db:migrate` (миграция 009 добавляет устойчивые намерения очистки).
