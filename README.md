# Файловый сервис

Демо-сервис хранения файлов: REST API на Express поверх Cloud.ru Object Storage (S3-совместимое) с
метаданными в PostgreSQL и одностраничный клиент на Vue 3. Файлы лежат в объектном хранилище, а всё,
что о них известно — исходное имя, папка, размер, статус, — живёт в базе.

| Часть | Что это | Документация |
|---|---|---|
| `server/` | REST API, S3 и PostgreSQL | [server/README.md](server/README.md) |
| `client/` | SPA: загрузка, список, карточка файла | [client/README.md](client/README.md) |

там, а не здесь.

## Возможности

**Три сценария загрузки, одна и та же запись на выходе.** Через сервер — обычная
`multipart/form-data`-форма, байты идут через API, потолок задаёт `MAX_UPLOAD_SIZE_MB`. Напрямую в
хранилище — клиент получает presigned-ссылку и льёт файл сам, минуя процесс API. Частями — для
файлов от `MULTIPART_THRESHOLD_MB`: сервер присылает готовый план (`offset`/`size`/`url` каждой
части), клиент исполняет его параллельно. Для остального интерфейса все три неразличимы.

**Multipart переживает сбои.** Части льются с ограниченной параллельностью, протухшую подпись
заменяет `part-urls`, а `GET /:id/multipart` отвечает тем, что реально лежит в S3, — поэтому
прерванная загрузка продолжается с уже залитого, в том числе после перезагрузки страницы. Брошенную
загрузку клиент отменяет сам, а до забытых прибирается `npm run db:cleanup`.

**Папки поверх плоского хранилища.** В S3 папок нет: структуру даёт директория, которая становится
префиксом ключа объекта. Она же — единственный недоверенный ввод, попадающий в ключ, поэтому
нормализация отвергает `..` и управляющие символы, а не переписывает их. Дерево папок строится из
сохранённых путей, `fileCount` считает всё поддерево.

**Список с поиском, сортировкой и пагинацией.** Поиск идёт по текущей папке и подпапкам, сортировка
— по дате, имени или размеру, лимит страницы ограничен сверху сервером.

**Скачивание по временной ссылке.** Клиент не проксирует байты: он переходит по presigned-GET.
`Content-Disposition` восстанавливает исходное имя файла, включая не-ASCII, через RFC 5987
`filename*` — при том, что в хранилище объект называется `<uuid>.<ext>`.

**Ошибки со стабильными кодами.** Каждый провал API — это `{ error: { code, message, details?,
requestId } }`; клиент переводит `code` в текст и показывает «Код обращения», по которому причина
ищется в логе сервера. Внутренности зависимостей (SQLSTATE, имена ошибок AWS, ключи объектов) в
ответ не попадают. 502 и 503 разделены намеренно: повторять стоит только второе, и кнопка «Повторить»
появляется ровно там, где повтор осмыслен.

## Быстрый старт

Нужны PostgreSQL, бакет в Cloud.ru Object Storage и Node 20.19+ / 22.12+ (в репозитории — 24).

```bash
# сервер → http://localhost:3000
cd server && npm install
# создать .env — полный список ключей в server/README.md
npm run db:migrate         # схема, идемпотентно
npm run s3:cors            # один раз на бакет, иначе presigned-загрузки из браузера не пройдут
npm run dev

# клиент → http://localhost:5173
cd client && npm install
cp .env.example .env
npm run dev
```

Порт клиента закреплён: CORS бакета настроен ровно на `http://localhost:5173`, и молчаливый сдвиг на
5174 сломал бы presigned-загрузку. Запросы к API идут через vite-прокси, так что CORS сервера в
разработке не участвует.

## Стек

Сервер — Express 5, TypeScript, `pg`, AWS SDK v3, zod, pino, multer. Клиент — Vue 3
(`<script setup>`), TypeScript, Vite, Tailwind CSS v4, shadcn-vue, `vue-router`, `vue-sonner`, `@vueuse/core`.
Тесты с обеих сторон — Vitest (`npm test` в каждой папке).

## Границы демо

- **Пользователь один** — его логин и пароль задаёт окружение сервера (`LOGIN_USER_APP`,
  `PASSWORD_USER_APP`); регистрации и прав нет, файлы общие.
- **Удаление мягкое в базе и best-effort в хранилище**: источник истины — запись, поэтому её выводят
  из обращения первой.
- **HTTP-маршруты тестами не покрыты** — покрыта логика, которой не нужны ни S3, ни база.
