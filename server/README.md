# Файловый сервис — сервер

REST API для хранения файлов в Cloud.ru Object Storage (S3-совместимое) с метаданными в PostgreSQL.
Переданная клиентом «директория» становится префиксом ключа S3-объекта — именно это и даёт сервису
структуру папок, ведь в самом S3 никаких папок нет.

## Запуск

Все команды запуска ниже выполняются из корня репозитория. Зависимости устанавливаются
для обоих npm workspaces через единый lock-файл; серверные пакеты остаются в `server/node_modules`.
Создайте `server/.env` по таблице конфигурации ниже.

```bash
npm ci
npm run db:migrate     # создать схему (идемпотентно)
npm run s3:cors        # один раз на бакет, необходимо для presigned-загрузок из браузера
npm run dev:server
```

`npm run dev` из корня запускает оба сервиса. Таблица ниже описывает локальные скрипты сервера:
из корня используйте `npm run <script> -w server`, из `server/` — команды таблицы.
Добавление зависимости из корня: `npm install <package> -w server`, для devDependency — с `-D`.

| Скрипт                                                    | Что делает                                                                                               |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `npm run dev`                                             | сервер в watch-режиме                                                                                    |
| `npm run build` / `npm start`                             | сборка в `dist/` и запуск                                                                                |
| `npm run typecheck`                                       | `tsc` по `tsconfig.test.json` — исходники и тесты одним проходом                                         |
| `npm test`                                                | один прогон vitest                                                                                       |
| `npm run test:watch`                                      | vitest в watch-режиме                                                                                    |
| `npm run test:coverage`                                   | покрытие (нужен `@vitest/coverage-v8`)                                                                   |
| `npm run db:migrate`                                      | применяет `src/db/migrations/*.sql`, история в `schema_migrations`                                       |
| `npm run notification:test -- --to recipient@example.com` | отправляет тестовое письмо через настроенный SMTP                                                        |

## API

`/health` и `/health/ready` открыты. Всё под `/api` требует `Authorization: Bearer <токен доступа>`,
кроме `/api/auth/*` и документации. Токен проверяется только по подписи, сроку и типу, без базы.

### Аутентификация

Зарегистрированный активный пользователь вводит email и пароль, затем шестизначный код из письма.
Неизвестный email и неверный пароль дают одинаковый 401; только правильный пароль
неактивного пользователя даёт 403 EMAIL_NOT_VERIFIED. Старые LOGIN_USER_APP и PASSWORD_USER_APP
игнорируются, пользователь из окружения при старте не создаётся и не синхронизируется.

| Эндпоинт                                             | Успех                                                                                                      | Особые ошибки                                                                                 |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| POST /api/auth/login `{ email, password }`           | 200: attemptToken, attemptExpiresAt, codeExpiresAt, resendAvailableAt, deliveryStatus; без cookie и сессии | 401 INVALID_CREDENTIALS, 403 EMAIL_NOT_VERIFIED                                               |
| POST /api/auth/login/resend `{ attemptToken }`       | 200: attemptExpiresAt, codeExpiresAt, resendAvailableAt, deliveryStatus; без пароля                        | 410 LOGIN_ATTEMPT_INVALID, 429 сохраняет прежний код и сроки                                  |
| POST /api/auth/login/verify `{ attemptToken, code }` | 200: accessToken, expiresIn, user с id, name, email; cookie                                                | 400 LOGIN_CODE_INVALID с remainingAttempts, 400 LOGIN_CODE_EXPIRED, 410 LOGIN_ATTEMPT_INVALID |
| POST /api/auth/refresh                               | Тот же ответ сессии и тот же refresh-токен с новым сроком                                                  | 401 SESSION_EXPIRED очищает cookie, временный 503 сохраняет                                   |
| POST /api/auth/logout                                | 204: отзыв текущей сессии и очистка cookie; повтор также 204                                               | 503 сохраняет cookie                                                                          |

Восстановление пароля доступно активному и неактивному пользователю. `POST /api/auth/password-reset/request { email }`
даёт тот же нейтральный 202, что и повтор активации, через общий бюджет 15 секунд; ссылка
`https://files.example.com/password-reset#token=...` живёт 30 минут и заменяет прежнюю до SMTP,
в БД хранится только SHA-256 с назначением `password-reset`. Квота назначения — одно письмо в минуту
и пять в час по email, IP-квота писем общая. Сам запрос доступ не отзывает.
`POST /api/auth/password-reset/confirm { token, password, passwordConfirmation }` (20 запросов за
15 минут с IP, включая ошибочные тела) атомарно сохраняет пароль, активирует пользователя, погашает
все ссылки активации и восстановления, завершает незавершённые попытки входа и отзывает сессии;
вход не выполняется. Ошибки полей — 422 без расходования ссылки, любая недействующая ссылка —
`400 PASSWORD_RESET_LINK_INVALID`. После сохранения — одна SMTP-попытка уведомления
«Ваш пароль изменён» без ссылок; её сбой результат не отменяет. Выданные токены доступа
сохраняют остаточный срок.

Попытка действует 15 минут, код — пять минут, включая ведущие нули. Пятая ошибка завершает
попытку; ошибка формата расходует общий лимит проверок, но не пять ошибок. Даты UTC ISO 8601,
таймеры клиента учитывают серверный Date. Первый шаг ограничен 10 запросами за 15 минут по email
и 50 с IP; проверки — 20 по пользователю и 100 с IP за 15 минут. Счётчики в PostgreSQL общие
для экземпляров, учитывают ошибочные запросы и переживают перезапуск.

Письма кода ограничены одним в минуту и пятью в час по email и назначению, совместно со всеми
письмами доступа — 20 в час с IP. После правильного пароля превышение возвращает 429 с
Retry-After и details.retryAfterSeconds без новой попытки или письма. Попытка сохраняется до
одной SMTP-попытки в пределах общего бюджета запроса 15 секунд. accepted означает принятие
почтовым сервером; unconfirmed сохраняет ввод кода при отказе, таймауте и неизвестном результате.
Ошибка сохранения даёт 503 без письма; автоматических повторов и досылки нет.

Повтор кода атомарно заменяет код действующей попытки до SMTP; новый код живёт пять минут, но не
дольше попытки. Срок попытки, неверные проверки и лимиты проверок не сбрасываются. Первый код и
повторы делят квоту писем назначения «код входа»; IP-квота писем учитывает и неизвестные попытки,
и некорректные тела. Отказ по лимиту или ошибка записи оставляют прежний код и сроки.

Пароли хешируются scrypt. Секрет попытки случаен; в БД только хеш. Код защищён HMAC
с отдельным AUTH_CODE_SECRET, привязкой к попытке и назначению. Успешное погашение и создание
сессии атомарны. После потерянного ответа полученная cookie позволяет refresh, иначе нужен новый вход.
Токен доступа — JWT HS256 на 15 минут в памяти клиента; проверяется без БД и сохраняет остаточный
доступ до истечения даже после выхода. Токен обновления — случайный постоянный секрет;
в PostgreSQL хранятся его хеш, пользователь, сроки и состояние. Каждое успешное продление
заново отсчитывает семь дней, без общего календарного предела; параллельные повторы разрешены.
Выход отзывает одну сессию и не затрагивает другие браузеры.

Cookie refresh_token: HttpOnly, Secure, SameSite=Strict, Path=/api/auth, без Domain, Max-Age=604800.
HTTP и COOKIE_SECURE=false допустимы только локально; рабочие AUTH_ALLOWED_ORIGINS должны
быть HTTPS. Все auth-маршруты требуют разрешённый Origin и возвращают Cache-Control: no-store.
Секреты, cookie и адреса получателей не журналируются. Решение —
[ADR-0007](../docs/adr/0007-autentifikatsiya-polzovatelya-iz-okruzheniya.md).

Полная координация вкладок, владение файлами и чистый переход — соседние задачи #75.
До итоговой проверки перехода сервис нельзя открывать: файлы пока общие.

Контракт описан в `openapi.json` — он собирается из Zod-схем запросов и ответов
(`src/modules/files/adapters/http/schemas.ts`, `responses.ts`, `openapi.ts`) командой
`npm run openapi` и коммитится; клиент генерирует из него типы. Тест `src/openapi.test.ts` падает,
если файл устарел или маршрут не описан. Почему так — [ADR-0006](../docs/adr/0006-kontrakt-api-iz-zod-shem.md).

Swagger UI — `/api/docs` (через vite-прокси: `http://localhost:5173/api/docs`). Токен доступа из
ответа `POST /api/auth/login/verify` вводится в **Authorize** и переживает перезагрузку страницы. Включается `API_DOCS_ENABLED`.

### Ошибки

Ответ с ошибкой всегда имеет один и тот же вид:

```jsonc
{
  "error": {
    "code": "STORAGE_UNAVAILABLE", // стабильный код, по нему клиент выбирает текст
    "message": "Object storage is unreachable right now; please try again shortly",
    "details": { "operation": "PutObject" }, // необязательное, зависит от кода
    "requestId": 42, // тот же id, что и в строке лога
  },
}
```

`requestId` присваивает `pino-http`; по нему в логе находятся и access-строка, и строка ошибки —
это единственный способ связать жалобу клиента с тем, что реально произошло на сервере. Внутренности
зависимостей (имя ошибки AWS, ключ объекта, SQLSTATE, имя констрейнта) в ответ не попадают: они
уходят только в лог.

| Код                                      | Статус | Когда                                                                              |
| ---------------------------------------- | ------ | ---------------------------------------------------------------------------------- |
| `UNAUTHORIZED`                           | 401    | нет токена доступа, он истёк или недействителен                                    |
| `INVALID_CREDENTIALS`                    | 401    | вход не удался; не говорит, что именно неверно — email или пароль                  |
| `SESSION_EXPIRED`                        | 401    | продление не удалось: нет cookie, токен истёк или сессии отозваны — нужен вход     |
| `ROUTE_NOT_FOUND`                        | 404    | такого маршрута нет                                                                |
| `VALIDATION_ERROR`                       | 422    | не прошла zod-схема; `details` — `{ formErrors, fieldErrors }`                     |
| `FILE_REQUIRED`                          | 400    | в `multipart/form-data` нет поля `file`                                            |
| `INVALID_DIRECTORY`, `INVALID_FILE_NAME` | 400    | путь или имя не пережили нормализацию                                              |
| `UPLOAD_REJECTED`                        | 400    | multer отверг форму (лишнее поле, больше одного файла)                             |
| `PAYLOAD_TOO_LARGE`                      | 413    | файл больше `MAX_UPLOAD_SIZE_MB` — нужен presigned-сценарий                        |
| `FILE_NOT_FOUND`                         | 404    | записи нет или она уже удалена                                                     |
| `FILE_NOT_READY`                         | 409    | файл ещё не `ready`, скачивать нечего                                              |
| `UPLOAD_NOT_COMPLETED`                   | 409    | по зарезервированному ключу так и не появился объект                               |
| `INVALID_UPLOAD_SIZE`                    | 400    | `size` не положительное число                                                      |
| `INVALID_PART_NUMBER`                    | 400    | номер части вне `1..partCount` либо в запросе больше `MULTIPART_URL_BATCH` номеров |
| `MULTIPART_NOT_FOUND`                    | 409    | у записи нет незавершённой multipart-загрузки                                      |
| `MULTIPART_INCOMPLETE`                   | 409    | при завершении в хранилище лежат не все части                                      |
| `TOO_MANY_ACTIVE_UPLOADS`                | 429    | исчерпан `MULTIPART_MAX_ACTIVE_UPLOADS`                                            |
| `DUPLICATE_RESOURCE`                     | 409    | нарушен уникальный индекс                                                          |
| `STORAGE_MISCONFIGURED`                  | 502    | S3 отверг запрос: не тот бакет или ключи                                           |
| `STORAGE_ERROR`                          | 502    | S3 ответил тем, с чем сервис работать не может                                     |
| `STORAGE_UNAVAILABLE`                    | 503    | до S3 не достучаться                                                               |
| `DATABASE_TIMEOUT`                       | 503    | запрос снят по `statement_timeout`                                                 |
| `DATABASE_UNAVAILABLE`                   | 503    | БД недоступна                                                                      |
| `INTERNAL_SERVER_ERROR`                  | 500    | всё остальное; вне production в `details` кладётся стек                            |

Разделение 502 и 503 намеренное: 502 повторять бессмысленно (сломана конфигурация — это чинится
деплоем), 503 — стоит, зависимость может ответить через секунду. `TOO_MANY_ACTIVE_UPLOADS` — про
занятые слоты, а не про частоту запросов: автоматический повтор упрётся в тот же занятый слот, место
освобождает только `complete` или `DELETE` одной из идущих загрузок.

### Загрузка

Оба сценария создают запись одного и того же вида и взаимозаменяемы с точки зрения клиента.

**Через сервер** — просто, ограничено `MAX_UPLOAD_SIZE_MB`:

```
POST /api/files          multipart/form-data: file, directory?
→ 201 FileDto
```

**Напрямую в S3** — для файлов побольше; байты не проходят через процесс API:

```
POST /api/files/presign-upload   { filename, directory?, contentType?, size? }
→ 201 { id, key, directory, uploadUrl, expiresAt, requiredHeaders }

PUT <uploadUrl>                  ровно с теми заголовками, что в requiredHeaders
                                 (Content-Type входит в подпись)

POST /api/files/:id/complete
→ 200 FileDto
```

Вызов `complete` не опционален. Пока он не выполнен, запись остаётся в статусе `pending`, и именно он
заполняет `size` и `etag` — они вычитываются из S3 через `HeadObject`, а не берутся на веру у клиента.
Вызов идемпотентен и возвращает `409 UPLOAD_NOT_COMPLETED`, если по зарезервированному ключу так и не
появился объект или его размер не совпадает с ожидаемым. Поздний целый объект может восстановить
неподтверждённую загрузку, но окончательно отменённые и очищенные операции больше не принимают
подтверждение и не возвращаются в готовые.

**Частями напрямую в S3** — для файлов, которые не стоит лить одним запросом. Тот же
`presign-upload`: если в теле есть `size` и он не меньше `MULTIPART_THRESHOLD_MB`, ответ приходит с
`strategy: "multipart"` вместо `strategy: "single"`. Без `size` сценарий всегда single.

```
POST /api/files/presign-upload   { filename, directory?, contentType?, size }
→ 201 { strategy: "multipart", id, key, directory, uploadId, size, partSize, partCount,
        maxConcurrency, expiresAt,
        parts: [{ partNumber, offset, size, url }, …] }   // первые MULTIPART_URL_BATCH

PUT <parts[i].url>               тело = file.slice(offset, offset + size)
                                 не больше maxConcurrency запросов одновременно

POST /api/files/:id/multipart/part-urls   { partNumbers: [ … ] }
→ 200 { expiresAt, parts: [{ partNumber, offset, size, url }, …] }

GET  /api/files/:id/multipart
→ 200 { id, uploadId, size, partSize, partCount, uploadedParts, uploadedBytes }

POST /api/files/:id/complete     → 200 FileDto
DELETE /api/files/:id            → 204 (отменяет незавершённую загрузку)
```

**На сколько частей резать, решает сервер.** `src/modules/files/upload-plan.ts` получает желаемый
`partSize` из политики загрузки и, если частей выходит больше `MULTIPART_MAX_PARTS`, увеличивает часть до
`ceil(size / maxParts)`, округлённого вверх до мегабайта. Клиент получает готовые `offset`/`size` и
ничего не пересчитывает.

| Размер файла | `partSize` | `partCount`           |
| ------------ | ---------- | --------------------- |
| 80 МиБ       | —          | `strategy: "single"`  |
| 100 МиБ      | 16 МиБ     | 7 (последняя — 4 МиБ) |
| 1 ГиБ        | 16 МиБ     | 64                    |
| 160 ГиБ      | **17 МиБ** | 9 638                 |

Последняя часть почти всегда меньше 5 МиБ — правило минимума на неё не распространяется.

`part-urls` выдаёт и следующую пачку ссылок, и замену протухшим: подписи живут
`PRESIGN_PART_TTL_SECONDS`, а загрузка может идти дольше. `GET /:id/multipart` отвечает тем, что
реально лежит в S3, — этого достаточно, чтобы продолжить прерванную загрузку, в том числе после
перезагрузки страницы.

Завершение и отмена — **те же маршруты, что у single-сценария**. `complete` смотрит на запись: если
это multipart, он собирает объект из частей и только потом читает результат через `HeadObject`.
`DELETE` по незавершённой загрузке делает `AbortMultipartUpload`, а не `DeleteObject`: объекта по
ключу ещё нет, убирать надо залитые части.

### Чтение

```
GET /api/files?directory=&recursive=&search=&status=&page=&limit=&sort=&order=
→ { items: FileDto[], pagination: { page, limit, total, totalPages } }
```

`directory` сопоставляется точно, если не указано `recursive=true`. `status` по умолчанию `ready`
(`any` — все), `limit` ограничен сверху значением 200, `sort` — одно из `created_at` |
`original_name` | `size_bytes`.

```
GET /api/files/:id?withUrl=true          → FileDto (withUrl добавляет свежий downloadUrl)
GET /api/files/:id/download-url?disposition=attachment|inline&expiresIn=
                                         → { url, expiresAt, name }
DELETE /api/files/:id                    → 204
POST /api/directories                   { parent?, name } → 201 { name, path, fileCount }
GET /api/directories?parent=docs         → { parent, items: [{ name, path, fileCount }] }
```

`/api/directories` читает самостоятельные постоянные каталоги, включая пустые; `fileCount` учитывает всё
поддерево. Ссылки на скачивание несут `Content-Disposition`, восстанавливающий исходное имя файла,
включая не-ASCII, через RFC 5987 `filename*`.

### FileDto

```jsonc
{
  "id": "a5e1ee53-…", // он же — базовое имя ключа S3
  "name": "Отчёт за Q3.pdf", // исходное имя, сохраняется в БД
  "directory": "docs/reports", // нормализовано: без ведущих/конечных/повторяющихся слэшей
  "extension": "pdf",
  "contentType": "application/pdf",
  "size": 74, // null, пока presigned-загрузка не подтверждена
  "etag": "\"9020e7b4…\"",
  "status": "ready", // pending | ready | failed
  "uploadSource": "server", // server | presigned | multipart
  "bucket": "bucket-4f84ee",
  "key": "docs/reports/a5e1ee53-….pdf",
  "createdAt": "2026-08-27T12:45:43.437Z",
  "updatedAt": "2026-08-27T12:45:43.437Z",

```

## Заметки по устройству

- **Ключи объектов — это `<directory>/<uuid>.<ext>`,** а не исходное имя файла. Поэтому ключ известен
  ещё до того, как появятся байты, — именно это делает возможным presigned-сценарий, — а загрузки не
  могут ни столкнуться друг с другом, ни споткнуться о символы, неудобные в URL. Отображаемое имя
  живёт в базе и возвращается через `Content-Disposition`.
- **Строка директории — единственный недоверенный ввод, попадающий в ключ,** поэтому
  `normalizeDirectory` в `src/storage/keys.ts` прямо отвергает `..`, управляющие символы и слишком длинные
  сегменты, а не пытается их переписать.
- **Удаление мягкое в базе и устойчивое в хранилище.** Намерение очистки сохраняется до удаления;
  неудачную попытку и поздно появившийся объект убирает серверная фоновая задача.
- **Частями multipart-загрузки владеет S3, а не база.** Отдельной таблицы частей нет: при завершении
  и при возобновлении список берётся из `ListParts`. Это то же решение, по которому `size` и `etag`
  вычитываются из `HeadObject`, и оно же бесплатно даёт возобновление с другой вкладки или машины. В
  записи живут только `upload_id`, `part_size` и `part_count`, и все три обнуляются, как только
  загрузка завершилась или была разобрана.
- **Запросы одной операции загрузки сериализуются блокировкой PostgreSQL.** Намерение отмены
  сохраняется независимо от блокировки, а запись готового результата отклоняется при наличии
  окончательного намерения очистки. Уборка просроченной операции использует ту же блокировку.
- **`src/middleware/validate.ts`** кладёт провалидированные query-строки и параметры маршрута в
  `res.locals`, потому что в Express 5 `req.query` доступен только на чтение.

Vitest, конфигурация в `vitest.config.ts`.

## Email-уведомления

Серверные сценарии используют `createNotification()` из `src/composition.ts`, затем ожидают
`notification.sendEmail({ to, subject, text, html? })`. SMTP-адаптер собирается через публичный
фасад `modules/notification/index.ts`. Вызов принимает ровно один email; тема и текст обязательны,
HTML при наличии непустой и передаётся вместе с текстом. Подготовка содержимого принадлежит
вызывающему сценарию. Получатель не обязан быть пользователем сервиса. Отправитель берётся
только из конфигурации; несколько получателей, CC и BCC не поддерживаются.

Результат `{ messageId: string }` означает принятие единственного получателя SMTP-сервером,
а не доставку в ящик или прочтение. Проверка формата email не подтверждает существование ящика.
`NotificationError` из фасада имеет стабильный `code`: `INVALID_EMAIL_MESSAGE` при некорректном
письме, `NOTIFICATION_DISABLED` при выключенных уведомлениях и `EMAIL_SEND_FAILED` при отказе
получателя, сетевом сбое или таймауте. Детали Nodemailer скрыты. Письма и пароль не логируются.

Каждый вызов ожидает ровно одну попытку без повторов, пула соединений, очереди или сохранения
задания. После обрыва соединения ошибка не доказывает, что письмо не принято: повторный вызов
может создать дубль. При аварии процесса незавершённая отправка может потеряться.

Создание модуля и запуск HTTP-сервера не подключаются к SMTP. Его недоступность не блокирует
работу файлового сервиса и не включена в readiness. Три таймаута ограничивают разные этапы;
таймаут бездействия не задаёт общий срок отправки. Оба режима требуют шифрования с проверкой
сертификатов: `implicit` начинает с TLS, `starttls` требует STARTTLS и не допускает перехода к
незашифрованному соединению. Смена SMTP-провайдера требует только изменения конфигурации.

Пример Gmail: `SMTP_HOST=smtp.gmail.com`, порт `465` и `SMTP_TLS_MODE=implicit` либо порт `587`
и `SMTP_TLS_MODE=starttls`. Укажите полный email в `SMTP_USER`, разрешённый адрес в `SMTP_FROM`
и пароль приложения Google в `SMTP_PASSWORD`. Для аккаунта должны быть включены двухэтапная
проверка и доступна выдача паролей приложений; OAuth2 здесь не используется.
См. [SMTP Gmail](https://developers.google.com/workspace/gmail/imap/imap-smtp),
[пароли приложений Google](https://support.google.com/accounts/answer/185833?hl=ru) и
[SMTP Nodemailer](https://nodemailer.com/smtp).

Автотесты подменяют транспорт и Nodemailer без сети и реальных писем. Ручная проверка через
Gmail после настройки аккаунта проводится отдельно и не требуется для `npm run check`.

### Ручная проверка SMTP

1. Заполните `server/.env` по `server/.env.example`, включая общие обязательные настройки
   сервера. CLI валидирует ту же конфигурацию, хотя не запускает HTTP-сервер и не подключается
   к PostgreSQL или объектному хранилищу.
2. Установите `NOTIFICATION_ENABLED=true` и настройки SMTP. Для Gmail:

   ```dotenv
   NOTIFICATION_ENABLED=true
   SMTP_HOST=smtp.gmail.com
   SMTP_PORT=465
   SMTP_TLS_MODE=implicit
   SMTP_USER=sender@gmail.com
   SMTP_PASSWORD=<пароль приложения Google>
   SMTP_FROM=sender@gmail.com
   ```

   Для обязательного STARTTLS укажите `SMTP_PORT=587` и `SMTP_TLS_MODE=starttls`.
   Пользователь — полный email, отправитель должен быть разрешён выбранным SMTP-сервером.
   Пароль приложения доступен при включённой двухэтапной проверке, если выбранный аккаунт
   допускает его выдачу. Пароль задаётся только окружением, аргументы CLI его не принимают.

3. При необходимости задайте отдельные таймауты: `SMTP_CONNECTION_TIMEOUT_MS=10000`
   для установления соединения, `SMTP_GREETING_TIMEOUT_MS=10000` для приветствия SMTP,
   `SMTP_SOCKET_TIMEOUT_MS=30000` для бездействия. Они не гарантируют общий срок отправки.
4. Из корня репозитория выполните:

   ```bash
   npm run notification:test -w server -- --to recipient@example.com
   ```

Команда принимает одного получателя и отправляет одно письмо с фиксированными тестовыми темой
и текстом через обычную сборку модуля. Она ожидает ответ SMTP. Код `0` и `EMAIL_ACCEPTED`
означают принятие единственного получателя SMTP-сервером; доставка в ящик и прочтение
не подтверждаются. Код `1` сопровождается причиной: `INVALID_ARGUMENTS` для отсутствующего
или некорректного `--to`, `NOTIFICATION_DISABLED` для выключенных уведомлений,
`INVALID_EMAIL_MESSAGE` для некорректного письма, `EMAIL_SEND_FAILED` для отказа SMTP,
сетевого сбоя или таймаута. Ошибки общей конфигурации также завершают команду ненулевым кодом.
Пароль и содержимое письма в диагностику не попадают.

После обрыва соединения или таймаута результат может остаться неизвестным: ошибка не доказывает,
что SMTP не принял письмо. Повторный запуск может создать дубль; автоматических повторов нет.
Реальную проверку выполняет оператор отдельно после настройки аккаунта. Она не входит
в автоматические тесты и не требуется для их прохождения.

### Окончательная отмена и фоновая очистка

`POST /api/files/upload-operations/:id/cancel` сохраняет окончательное намерение отмены
до получения блокировки операции. После удаления объекта и частей возвращает `cancelled`,
пока передача ещё обрабатывается — `processing`. Отмена удаляет и уже готовый файл;
повторная передача с прежним UUID запрещена. Отмена до резервирования также сохраняется.

`POST /api/files/upload-operations/:id/fail` завершает подтверждённую неудачу после исчерпания
повторов. Обнаруженный целый файл возвращается как `succeeded`; иначе остатки удаляются
и возвращается `discarded`. Ручной повтор окончательно завершённой операции требует нового
UUID. GET состояния также возвращает `cancelled` и `discarded`.

Миграция 009 добавляет `upload_terminations`. Сервер каждые 15 секунд повторяет сохранённые
отмены, удаления и окончательные неудачи, а также выполняет обычную уборку просроченных
резервирований. Намерения остаются после очистки: поздний PUT по старой ссылке не должен
восстанавливать отменённый файл. Каждый проход рассматривает до 100 завершённых операций
с ротацией по времени проверки. `npm run db:cleanup` выполняет такой же проход вручную.
Удаление через `DELETE /api/files/:id` также сохраняет задачу очистки и допускает повтор;
при сбое хранилища возвращает ошибку, а сервер продолжает очистку независимо от клиента.
Подтверждение и восстановление проверяют фактический размер объекта против ожидаемого,
если размер был указан при резервировании.

### Регистрация и первое письмо активации (#76)

`POST /api/auth/register` принимает `name`, `email`, `password` в JSON до 16 КиБ.
Имя после trim — 1–100 Unicode-кодовых точек; email после trim и lower-case — корректный адрес
до 254 символов с сохранением точек и `+`-части. Пароль — 12–128 кодовых точек без преобразования,
хешируется существующим scrypt. Миграция `012_registration.sql` добавляет email, имя, состояние,
секреты и устойчивые события квот. Старые строки остаются совместимыми до отдельного чистого перехода.
Пути `/api/auth/register`, `/api/auth/register/` и `/api/auth/REGISTER` по правилам
сопоставления Express — одна операция: Origin, общий срок, IP-квота и разбор тела
применяются одинаково, квота IP общая для всех вариантов.

Все auth-запросы проверяют `AUTH_ALLOWED_ORIGINS`: отсутствующий, `null` и чужой Origin дают
`403 ORIGIN_NOT_ALLOWED`; ответы содержат `Cache-Control: no-store` и `Referrer-Policy: no-referrer`.
Для нейтрального допущенного запроса ответ одинаков: `202` с message
«Если требуется письмо, инструкции придут на email» и `retryAfterSeconds` (обычно 45).
Общие 15 секунд отсчитываются после проверки Origin, до IP-квоты, и включают получение
тела, квоты, ожидание соединения с БД и SQL-блокировок, scrypt, сохранение и одну SMTP-попытку.
Если тело не получено или окончательная запись не подтверждена к концу срока, сервер
возвращает `503 SERVICE_UNAVAILABLE` без запуска SMTP и закрывает соединение с недочитанным телом.
Позднее получение тела не создаёт
пользователя. Неизвестный результат записи не означает откат: сохранённые пользователь,
секрет и израсходованные квоты не удаляются принудительно; повтор выполняется вручную.
Активному пользователю не создаётся активация, повторная регистрация не меняет имя и пароль.
Новая активация
неактивного пользователя заменяет прежний проверочный хеш до SMTP. Ссылка имеет вид
`https://files.example.com/activation#token=...`, живёт 24 часа; в БД хранится только SHA-256.
Подтверждение ссылки и ручной повтор реализуются следующей задачей; сервис пока не готов
к открытому многопользовательскому доступу.

IP-квота писем — 20 за скользящий час, включая неправильные поля и транспортные ошибки.
Квота нормализованного email и назначения activation — одно письмо в минуту и пять в час;
её будет использовать и повтор активации. Событие на левой границе окна исключается.
Счётчики хранятся в PostgreSQL; блокировки действуют между экземплярами. Окна учитываются
независимо: отказ по одному пределу не сдвигает его события, остальные применимые счётчики
продолжают учитывать запрос в пределах своих квот. Отказ возвращает
`429 RATE_LIMITED`, `Retry-After` и `details.retryAfterSeconds`, округлённые вверх.
При сбое проверки или записи — `503 SERVICE_UNAVAILABLE`, без отправки.

События квот не хранятся для аудита: подсчёт сам учитывает только события строго после
левой границы окна, а физическое удаление выполняет фоновая уборка. Событие можно удалить
по окончании его собственного окна — минутное через минуту, часовое через час — независимо
от повторных обращений к тому же email или IP. Уборка запускается при старте сервера и
каждые 15 секунд на каждом экземпляре, отдельно от уборки загрузок; один проход удаляет
не более 1000 событий одним запросом, остаток обрабатывают следующие проходы, проходы на
одном экземпляре не перекрываются. Строки выбираются с `skip locked`, поэтому параллельные
проходы экземпляров безопасны. Отдельного индекса нет: в таблице остаются события не старше
часа, полный просмотр такой таблицы дешёвый. Проход ограничен 15 секундами ожидания пула
и SQL. Пользователи и секреты активации не затрагиваются.
Сбой уборки записывается в журнал без email и секретов и повторяется следующим проходом;
регистрация продолжает работать, пока исправны проверка и запись квот.

SMTP получает оставшуюся часть общего бюджета и закрывает соединение при его истечении.
Принятие, отказ, таймаут или неизвестный результат не удаляют пользователя и секрет.
Очереди, автоматических повторов и досылки после перезапуска нет. Принятие SMTP не гарантирует
доставку. Логи auth не содержат полей формы, query string, заголовков доступа и исходных
ошибок SQL/SMTP; диагностика письма содержит только назначение, исход, длительность и requestId.

Рабочее окружение требует HTTPS, настроенных SMTP и отправителя. У reverse proxy отключите
журналирование тела и query string auth-запросов и задайте таймаут ответа минимум 30 секунд;
в `TRUSTED_PROXIES` перечислите только его фактические адреса/сети. Клиент и API используют
один origin. Изменение `CORS_ORIGIN` не заменяет настройку `AUTH_ALLOWED_ORIGINS`.
Для локальных тестов используйте подменный транспорт и отдельную БД на порту 55431:
`npm run test:postgres`. Основные проверки не обращаются к реальным ящикам и бакету.
