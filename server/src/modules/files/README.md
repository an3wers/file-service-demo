# `modules/files`

Модуль разложен по слоям, и зависимости внутри него направлены строго внутрь:

```
                         index.ts (фасад)
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                      │
  adapters/http         adapters/persistence   adapters/storage*
        │                     │                      │
        └─────────────────────┼──────────────────────┘
                              │
                        application/
          (uploads · confirmation · catalog · cleanup)
                              │
                          domain/
              (stored-file · keys · upload-plan · upload-policy ·
               reservation · errors · ports/{file-rows,object-storage,clock})
```

`domain/` не знает никого. `application/` знает только `domain/`. `adapters/` и `testing/`
знают всё, но не друг друга — `testing/` подставляет вторые реализации портов из `domain/ports/`.
Единственное исключение — тестовый вход `testing/index.ts`, описанный ниже: он использует
HTTP-перевод результата. Рабочий фасад модуля — `index.ts`: он отдаёт две
обёртки общей сборки (`createFilesHttp`, `createFilesMaintenance`) и контракты их зависимостей. Третий экспорт —
`mapFilesError` — не сборка и не тип зависимостей, а сам шов перевода доменных ошибок в
`AppError`. Его передаёт обработчику ошибок `src/composition.ts` вместе с отображениями
других модулей; сам обработчик модулей не знает. Без реэкспорта сборка не смогла бы
дотянуться до `adapters/http/error-map.ts`, не пробив фасад. Четвёртый и пятый — `filesPaths` и `directoriesPaths`: описание маршрутов модуля для
OpenAPI-документа, который собирает `src/openapi.ts`. Пути в них — относительно роутера, как в
`routes.ts`; префикс монтирования добавляет сборщик документа. Ни один доменный тип и ни один DTO
эту границу не пересекают — схемы ответов уходят наружу только как часть описания путей.

\* `adapters/storage/` в дереве нет: порт `ObjectStoreForFiles`/`ObjectStoreForMultipart`/
`ObjectStoreForCleanup` (в `domain/ports/object-storage.ts`) описан достаточно широко, чтобы
общий `storage/`'s `ObjectStore` подошёл под него без адаптера — сборка передаёт один и тот же
экземпляр всем сценариям как есть. Подробности и другие решения о границах — в
[ADR-0005](../../../../docs/adr/0005-sloi-i-granitsa-modulya-files.md).

## Что нельзя импортировать откуда

Проверяется линтером (`eslint.config.js`, правило `no-restricted-imports`), а не соглашением:

- **`domain/`** не импортирует `application/`, `adapters/` и `testing/` этого модуля, а также
  пакеты вендора (`pg`, `express`, `multer`, `@aws-sdk/*`) — это знание принадлежит адаптерам.
  `src/logger.ts` и типы общего `storage/` портом не считаются нарушением: они не адаптер и не
  слой этого модуля, а корневой shared kernel. Исключение — `src/errors.ts` и `src/db/errors.ts`:
  они несут HTTP-статусы, поэтому домен их не импортирует (см. «Ошибки» ниже).
- **`application/`** импортирует только `domain/` (плюс ту же общую инфраструктуру, по той же
  причине и с тем же исключением для ошибок) — не `adapters/`. Единственное исключение прописано в самом правиле построчно: тест
  сценария импортирует `testing/`, потому что иначе его нечем было бы собрать.
- **Снаружи модуля** виден `index.ts`; корню приложения также доступен `persistence.ts` —
  любой импорт на уровень глубже фасада, написанный спуском через `modules/files/...`, падает на
  линтере. Это ловит код, который лежит вне `src/modules` целиком (так и был пойман прежний прямой
  импорт `files.error-map.ts` из `error-handler.ts`); соседний модуль, дотянувшийся через `..`
  сбоку, а не спуском сверху, буквы `modules/files` в своём импорте не пишет и линтером пока не
  ловится — известный предел `no-restricted-imports`, разобран в `eslint.config.js` рядом с
  правилом.

Тестам из `client/integration/` разрешён один отдельный вход — `testing/index.ts`.
Он экспортирует сборку сценариев на memory-портах и перевод результата `toFileDto`.
Только этот вход внутри `testing/` импортирует `adapters/http/dto.ts`; клиентские тесты не
импортируют адаптеры или файлы тестовой сборки напрямую. Это явное тестовое исключение из
[ADR-0005](../../../../docs/adr/0005-sloi-i-granitsa-modulya-files.md), позволяющее проверить
настоящие API клиента и сценарии сервера без внешних сервисов. Рабочий код не использует
`testing/index.ts`, а рабочий фасад не экспортирует тестовую сборку. Проверка этого исключения
при ревью дополняет описанные выше правила линтера.

Пример: `import "pg"` внутри `domain/` — ошибка линтера, а не логическая; ни один тест не должен
на неё полагаться.

## Ошибки

Домен и сценарии бросают только классы из `domain/errors.ts`; HTTP-статус и код ответа
выбирает `adapters/http/error-map.ts`, сохраняя `details` и исходную ошибку как `cause`.
Маппер строк тоже бросает доменную `ImpossibleFileRowError`: она становится ответом 500,
а её `details` уходят только в лог. Ошибки общей инфраструктуры (`AppError` из `pool.ts` и
`storage/`) сценарии пропускают насквозь, не создавая их сами.

Memory-двойники бросают те же типы, что SQL-адаптеры. Это проверяет общий контракт
`testing/file-rows.contract.ts`: он запускается на двойнике в `npm test` и на PostgreSQL
в `npm run test:postgres`.

## Примеры принятых решений

Решения и их причины записаны в ADR; здесь — по одному наблюдаемому следствию каждого, без
пересказа.

- **Состояние — сумма типов, не пять независимых полей**
  ([ADR-0004](../../../../docs/adr/0004-sostoyanie-fayla-kak-summa-tipov.md)). Следствие:
  `LiveMultipartUpload.plan` существует только у файла в состоянии `"multipart"` — обратиться к
  плану готового файла невозможно на уровне типов, а не по соглашению «не читай это поле, пока
  проверяешь то». Проверка законности сочетания полей строки живёт ровно в одном месте —
  `adapters/persistence/row-mapper.ts` — и это единственный файл модуля, которому разрешено
  знать форму строки `FileRow` (`snake_case`, `Date`, `deleted_at`).

- **Порты узкие, а не один общий репозиторий**
  ([ADR-0002](../../../../docs/adr/0002-uzkie-interfeysy-repozitoriya-strok-metadannyh.md)).
  Следствие: `domain/ports/file-rows.ts` объявляет `FileRowsForFiles`, `FileRowsForMultipart` и
  `FileRowsForCleanup` отдельно, и `application/cleanup.ts` принимает только
  `FileRowsForCleanup` — он физически не может вызвать `insertFile`, потому что этого метода нет
  в типе, который ему передали. Тестовый `testing/memory-file-rows.ts` реализует объединение
  всех трёх, но каждый сценарий видит только свой срез.

- **Unit of Work не нужен** ([ADR-0005](../../../../docs/adr/0005-sloi-i-granitsa-modulya-files.md)).
  Следствие: `application/uploads.ts`'s `uploadThroughServer` пишет объект в хранилище, а затем
  строку в базу, и если вторая операция падает — откатывает первую сама, явным `catch`, а не
  транзакцией поверх двух хранилищ. Расхождение, которое эта ручная компенсация не поймает
  (например, ответ на вставку строки потерян, хотя вставка прошла), лечит `application/cleanup.ts`
  при следующем проходе — это тоже часть принятого решения, а не пробел.

## Подтверждение и неудавшаяся загрузка

`application/confirmation.ts` объединяет сверку с объектным хранилищем и переходы
строк метаданных. Сборки передают один экземпляр сценариям загрузки, удаления и уборки.

- `confirm` явно завершает составную загрузку и подтверждает фактические размер,
  ETag и тип содержимого. Повторное подтверждение возвращает готовый файл.
- `reconcile` выясняет исход без сборки частей. Отсутствующий объект до истечения
  попытки означает `pending`; просрочка или несовпадение размера — `failed`.
- `prepareRetry` дополнительно освобождает остановленную составную загрузку перед
  повтором через сервер. Неизвестный исход не разрешает новую передачу.
- `cleanup` исполняет сохранённое окончательное намерение отмены, удаления или
  неудачи и допускает повтор после частичного сбоя.

Неудача попытки записывается условно по текущему состоянию и поколению попытки.
Только выигравший обновление отменяет составную загрузку; конкурентное подтверждение
или новая попытка заставляют сверку перечитать состояние. Если отмена в хранилище
завершилась ошибкой после обновления строки, оставшиеся части удаляет уборка сирот.
Окончательная очистка отдельно сохраняет идентификатор загрузки для повторной отмены.

GET статуса операции читает сохранённый результат без блокировок и сверки хранилища.
Явная сверка выполняется POST-запросом разрешения операции. Значения `pending` и
`failed` уже отражены в Zod-схемах и сгенерированном `server/openapi.json`.

## Сборка

`assembly.ts` связывает сценарии один раз. HTTP-фасад, обслуживание и тестовый harness
используют эту фабрику с переданными портами. `composition.ts` выбирает S3 и фабрику
`createFilesPersistence` из отдельного входа `persistence.ts`; фасад не выбирает SQL.
Согласование политики с протоколом выполняется в корне, проверка плана — в общей сборке.
Обслуживание строит весь модуль с той же политикой, но вызывает только проход уборки.
Причины и граница входа хранения описаны в ADR-0005.
